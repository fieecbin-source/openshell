# ADR-002：前端框架选型 —— React vs Svelte

- 状态：已接受（M1）
- 日期：2026-10-21
- 关联：`docs/architecture.md` §6、§15、§18

## 背景

前端需要承载：会话树（可拖拽、虚拟列表、右键菜单）、多标签终端（xterm.js 实例生命周期管理）、SFTP 双栏文件管理器（大量行、拖拽、排序）、监控图表（1–5 s 更新）、转发/同步/设置表单、中英双语与明暗主题。约束是系统 WebView、单窗口、内存敏感、需要长期可维护。

候选：

1. React 18/19 + TypeScript
2. Svelte 5（runes）
3. SolidJS
4. Vue 3

## 选项对比

| 维度 | React | Svelte 5 | SolidJS | Vue 3 |
|---|---|---|---|---|
| 运行时体积（gzip） | ~45 KB | ~10 KB | ~8 KB | ~35 KB |
| 生态/组件/示例 | 最大 | 中 | 小 | 大 |
| xterm.js 集成 | 官方示例与大量实践 | 可用，实例管理需谨慎 | 可用 | 可用 |
| 细粒度更新 | 需 memo/外部 store | 编译期细粒度 | 信号原生 | 响应式 |
| 团队上手/招聘 | 最广 | 中 | 低 | 高 |
| 虚拟列表/表格 | TanStack Virtual 成熟 | 有，但生态小 | 少 | 成熟 |
| 类型支持 | 极好 | 好 | 好 | 好 |
| 复杂状态（终端/传输/连接） | 外部 store 模式成熟 | runes 较新 | 信号直观 | Pinia 成熟 |

体积差异（约 35 KB gzip）相对 25 MB 安装包与 150 MB 内存目标可以忽略；真正的成本在复杂状态管理与长期维护。

## 决策

采用 **React + TypeScript**，状态用 **Zustand**（按域切片），列表用 **TanStack Virtual**，样式用 **Tailwind**，构建用 **Vite**。

理由：

1. 终端管理是"命令式对象 + 声明式视图"的混合体：xterm 实例必须在 `useEffect`/ref 中精确控制生命周期，React 的显式模型更容易约束"何时创建/销毁/重挂载"。
2. 会话树、SFTP 表格、冲突解决对话框等复杂交互有成熟可借鉴的模式与库；Svelte 生态在虚拟化/表格上选择更少。
3. 多标签 + 分屏 + 拖拽重排属于高风险交互，React 的社区案例与调试工具（DevTools、Profiler）更利于排查渲染抖动。
4. TypeScript 与 Rust DTO 的映射可通过一套生成的类型/手写类型保持强约束。

不采用 Svelte 的理由：体积优势在本项目预算内不构成决定因素，而 runes 生态仍在演进；团队与后续 agent 协作对 React 的容错更高。

## 后果

**正面**

- 生态成熟：虚拟列表、拖拽、国际化、图表均有稳定选择。
- 渲染性能可通过 memo、虚拟化、选择性订阅控制。

**负面与缓解**

| 后果 | 缓解 |
|---|---|
| 运行时开销与重渲染风险 | 状态按域切片；终端数据**不进入 React state**（直接写 xterm）；列表虚拟化；避免 Context 大对象 |
| 包体积 | 不引入重型 UI 组件库；按需加载 SFTP/监控面板；Tailwind 原子类 + 构建期裁剪 |
| 终端实例与组件生命周期错配 | 终端容器为稳定 DOM 节点；`tab_id` 作为 key；切换标签只做 `display` 切换，不卸载实例 |
| 高频 IPC 事件触发渲染 | 事件在 `lib/ipc` 层聚合/节流（≥ 100 ms），只有 UI 需要的摘要进入 store |

## 验证与退出条件

- 1000 条会话滚动 p95 帧 ≤ 16.7 ms；4 标签终端输入回显 p95 ≤ 50 ms。
- 若 M3 结束前出现无法通过常规手段解决的重渲染瓶颈（长任务 > 100 ms 且影响输入），允许把**会话树/SFTP 表格**替换为轻量原生列表方案；整体框架替换需新 ADR。
