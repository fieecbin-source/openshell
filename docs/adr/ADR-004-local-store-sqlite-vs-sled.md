# ADR-004：本地存储 —— SQLite vs sled

- 状态：已接受（M1）
- 日期：2026-10-21
- 关联：`docs/architecture.md` §8、ADR-005、ADR-006

## 背景

本地需要持久化：会话树（分组/排序/标签/收藏/最近连接）、凭据密文、主机密钥、片段与宏、转发规则、标签布局、变更日志、同步出站队列/冲突/墓碑、设置与审计。典型规模：会话 10²–10⁴，记录总量 10⁴–10⁵，写入频率低但需要事务性（"实体写入 + 变更日志"必须原子）。

查询需求：按父节点取子树、按名称模糊搜索、按 `last_used_at` 排序、按标签过滤、分页、外键级联。

候选：

1. SQLite（`rusqlite`，`bundled` 编译，MIT；公共领域）
2. sled（纯 Rust 嵌入式 KV，MIT/Apache-2.0）
3. redb（纯 Rust KV，MIT/Apache-2.0）
4. 文件 + JSON（不可接受：无事务、无并发、迁移困难）

## 选项对比

| 维度 | SQLite (rusqlite bundled) | sled | redb |
|---|---|---|---|
| 数据模型 | 关系 + SQL + 索引 + FTS5 | KV（需自建索引） | KV（需自建索引） |
| 事务 | 完整 ACID，WAL | 单写事务 | 单写事务 |
| 并发 | 多读单写（WAL） | 多读单写 | 多读单写 |
| 查询能力 | JOIN/ORDER/LIMIT/聚合/全文 | 手动维护二级索引 | 手动维护二级索引 |
| 迁移 | SQL 脚本 + `user_version` | 自建版本键 | 自建版本键 |
| 生态/工具 | 极成熟，可在 CLI 中修复/备份 | 中等 | 较少 |
| 稳定性 | 20+ 年 | 0.34.x（长期未 1.0） | 1.x–2.x |
| 与服务端一致性 | 服务端也可用 SQLite/Postgres，SQL 心智一致 | 无 | 无 |
| 体积 | ~1 MB 编译进二进制（bundled） | < 1 MB | < 1 MB |
| 许可证 | MIT（SQLite 公共领域） | MIT/Apache-2.0 | MIT/Apache-2.0 |

## 决策

采用 **SQLite**（`rusqlite`，启用 `bundled`、`backup`），通过 `tokio-rusqlite` 提供单写者，WAL 模式，4 条只读连接。

理由：

1. 会话树/标签/搜索天然是关系查询；用 KV 需要自建多套索引，代码量与出错概率显著更高。
2. 事务边界正好匹配"业务写入 + `sync_record` 状态更新 + `sync_outbox` 入队"的原子性要求（ADR-006）。
3. `bundled` 特性把 SQLite 编进二进制，不需要系统库；三平台构建一致。
4. 备份/恢复（`VACUUM INTO`、`.backup`）和故障排查工具成熟，适合"用户自己部署/自己排障"的产品定位。
5. 服务端也用 SQL（sqlx + SQLite/Postgres），迁移与类型心智一致，减少团队切换成本。

不选 sled 的理由：仍是 0.34 系列，格式稳定性与长期维护承诺不足；无 SQL/索引/全文检索，会话搜索与分页需大量手工实现。

不选 JSON 文件的理由：无事务、无并发控制、无增量写、容易因崩溃损坏。

## 实现约束（决策的一部分）

1. `PRAGMA journal_mode=WAL; synchronous=NORMAL; busy_timeout=5000; foreign_keys=ON;`
2. 所有写操作经单写者任务；事务短（目标 < 5 ms），禁止在事务内做网络或 Argon2。
3. 迁移前自动 `VACUUM INTO` 备份；打开时若 `user_version` 高于程序支持版本则拒绝启动。
4. 加密不在 SQLite 层做（不引入 SQLCipher，避免额外 C 依赖与许可证/构建复杂度）：敏感列以应用层 AEAD 密文存储（ADR-005）。
5. 软删除 + 墓碑；物理清理由后台任务执行。
6. 会话量超过 2 000 时启用 FTS5 外部内容表；此前用 `LIKE` + 前缀索引。

## 后果

**正面**

- 复杂查询、分页、排序、外键一致性由数据库保证。
- 迁移可测试、可回滚（备份）。
- 服务端/客户端共享 SQL 经验。

**负面与缓解**

| 后果 | 缓解 |
|---|---|
| 单写者可能成为批量导入/同步应用瓶颈 | 分批提交（200 条/事务）；导入走独立队列；必要时合并 WAL checkpoint 策略 |
| 二进制内嵌 SQLite 增加约 1 MB | 在 25 MB 预算内可接受 |
| 数据库文件损坏风险 | WAL + `synchronous=NORMAL` + 迁移前备份 + 启动时 `PRAGMA quick_check`（失败则引导从备份恢复） |
| 加密列无法在 SQL 内比较/搜索 | 只加密密文列（口令/私钥）；需要搜索的字段保持明文索引（Q4 待澄清） |

## 验证与退出条件

- 并发测试：4 读 + 1 写持续 5 min，无 `SQLITE_BUSY` 泄漏到上层。
- 迁移测试：从每个历史 tag 的 fixture 升级成功。
- 1000 会话 + 10 000 变更日志下，列表查询 < 10 ms，搜索 < 30 ms。
- 若出现无法通过分批/索引解决的写瓶颈（例如同步应用 > 10 000 条/分钟需求），可评估拆分为"元数据库 + 变更日志独立库"；更换存储引擎需新 ADR。
