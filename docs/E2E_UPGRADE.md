# 真实升级演练（E2E）

单元测试只能证明「逻辑分支正确」，证明不了「用户真的能从 1.0.1 升到 1.0.2 且数据不丢」。
本文把这条链路拆成 5 个场景：能自动化的给出脚本，必须手动的给出带勾选框的步骤。

> 演练结论请回填到 `docs/ACCEPTANCE.md`（该文件含本机路径，按约定不入库）。

---

## 0. 前置条件

| 项 | 要求 |
| --- | --- |
| 已安装旧版 | `OpenShell v1.0.1`（本机或虚拟机，**先备份一份数据目录副本**） |
| 仓库权限 | 能推送 tag（正式演练），或只用本地/测试仓库 |
| 网络 | 能访问 `api.github.com` 与 `github.com`（否则先配代理） |
| 工具 | Node 20+（脚本用原生 `fetch`）、`git`、安装包签名无关 |

任何一步失败，先回滚：`git push --delete origin <tag>` → 删除 Release → 用第 6 节的清理步骤。

---

## 1. 场景一：跨版本升级数据完整（手动 + 自动）

**准备**

```bash
# 自动：发布侧元数据自检（预发布/正式都可）
node scripts/e2e-upgrade/check-release.mjs --repo fieecbin-source/openshell --tag v1.0.2-rc.1
```

**手动步骤**

1. [ ] 启动 1.0.1，创建 3 类真实数据：SSH 连接（含密码认证）、串口连接、1 个分组 + 2 张会话卡片。
2. [ ] 记下数据基线：连接数 3、分组 1、卡片 2，并记下数据目录路径（设置 → 关于与更新 → 数据目录）。
3. [ ] 在「关于与更新」把通道切到**测试**（rc 版本只在测试通道可见），点「检查更新」。
4. [ ] 确认弹窗显示 `1.0.1 → 1.0.2-rc.1`、发布说明、安装包大小。
5. [ ] 点「立即更新」，观察下载进度 → 校验 → 待安装。
6. [ ] 点「立即重启安装」，等安装器完成。
7. [ ] 重新打开客户端，逐项核对：
   - [ ] 连接仍是 3 个、分组 1 个、卡片 2 张，密码认证的 SSH 仍能连上；
   - [ ] 「关于与更新」显示版本 `1.0.2-rc.1`；
   - [ ] 数据目录 `backups/` 下出现 `openshell_1.0.1_pre-install_*.db`；
   - [ ] 数据库 `user_version` 为 2（可用 `sqlite3 openshell.db 'PRAGMA user_version;'`）。
8. [ ] 卸载/覆盖安装再启动一次，确认数据仍在（更新/卸载不删数据目录）。

**通过标准**：第 7、8 步全部勾选，且没有出现「数据已从备份恢复」横幅（正常升级不该出现）。

## 2. 场景二：迁移失败自动回滚（手动，需测试开关）

测试开关**只在 debug 构建中生效**，不得进入正式包：

```
OPENSHELL_FORCE_MIGRATION_FAILURE=1
```

1. [ ] 用 **debug 构建**（`pnpm tauri dev` 或 `cargo run -p openshell-desktop`）启动，并设置上述环境变量。
   实现位置：`backend/crates/store/src/migrator.rs` 的测试分支（若该开关尚未接线，见下方说明）。
2. [ ] 用一个 v1 数据库（从备份复制一份回来）启动。
3. [ ] 期望现象：
   - [ ] 应用仍能启动，`user_version` 保持 1；
   - [ ] 顶部出现琥珀色「数据已从备份恢复」横幅，含快照路径与时间；
   - [ ] 连接/分组数据完整可读。
4. [ ] 重启一次，确认横幅不再出现（避免每次启动都吓用户）。
5. [ ] `backups/` 下存在 `pre-migration-1-to-2-*.db` 快照。

> 若开关未接线：先手工把 `SCHEMA_VERSION` 临时改成 3 并让 v3 分支 `bail!`，同样能验证回滚路径。

## 3. 场景三：待安装状态跨会话恢复（手动）

1. [ ] 检查更新 → 下载完成 → 进入「安装包已就绪」后**不要点安装**。
2. [ ] 直接关闭客户端（任务管理器结束进程也算）。
3. [ ] 重新打开，打开更新弹窗：期望仍显示「安装包已就绪」并能直接安装。
4. [ ] 点「立即重启安装」，确认安装前**再次做 sha256 校验**（日志出现第二次 `sha256` 校验记录）。
5. [ ] 篡改测试：把 `updater/downloads/*.exe` 改掉一个字节后再点安装，期望报 `UPDATE_CHECKSUM_MISMATCH`
       并且不启动安装器。

## 4. 场景四：网络异常与文件异常（半自动）

```bash
# 断点续传 + 哈希不符（用真实 Release 的直链与 sha256）
node scripts/e2e-upgrade/verify-asset.mjs \
  --url <安装包直链> --sha256 <SHA256SUMS.txt 里的值> --out .e2e/downloads

# 模拟中途取消（超过 300KB 主动断开），然后再跑同一条命令续传
node scripts/e2e-upgrade/verify-asset.mjs --url <同一链接> --sha256 <同上> --out .e2e/downloads --abort-after 300000
```

| 子场景 | 操作 | 期望界面 | 结果 |
| --- | --- | --- | --- |
| 下载中断 | 断网 10s 后恢复 | 「下载中断」+ 重试（续传） | 未验证 |
| 中途取消 | 点「取消下载」 | 回到「发现新版本」，`.part` 保留 | 未验证 |
| sha256 不符 | 脚本传错误 `--sha256` | 报校验失败并删除临时文件 | 未验证 |
| 磁盘不足 | 把下载盘填到剩余 < 1.2×包体 | 下载前直接报空间不足 | 未验证 |

**磁盘不足的手动做法**：把数据目录指到一个小容量 U 盘（或用 `fsutil file createnew` 造大文件占满），
或在测试构建里注入 `SpaceProbe` 假实现（单测已覆盖 `InsufficientDisk` 分支）。

## 5. 场景五：检查失败不影响既有数据（手动，最容易被忽略）

1. [ ] 断网（或设置代理到不存在的端口），启动客户端。
2. [ ] 点「检查更新」→ 期望显示「检查更新失败」+ 重试，**没有**任何数据异常。
3. [ ] 关闭客户端，把系统时间改到 +30 天（触发自动检查），重启：
   - [ ] 自动检查失败不弹窗骚扰；
   - [ ] 连接、密钥、历史记录全部可正常使用。
4. [ ] 恢复网络，手动检查成功。

## 6. 演练后清理（正式推送 rc 时必须做）

```bash
# 1) 删除 Release（草稿或已发布）
gh release delete v1.0.2-rc.1 --yes --cleanup-tag

# 2) 删除远端 tag（若第 1 步没带 --cleanup-tag）
git push origin --delete v1.0.2-rc.1

# 3) 删除本地 tag
git tag -d v1.0.2-rc.1

# 4) 确认没有污染正式检测源
gh api repos/fieecbin-source/openshell/branches/updater-meta 2>/dev/null \
  && git ls-remote origin updater-meta   # rc 演练后该分支不应有新提交
```

- [ ] Release 已删除
- [ ] tag 已删除（远端 + 本地）
- [ ] `updater-meta` 分支没有任何 rc 相关提交
- [ ] 演练数据目录副本已归档（不要留在默认数据目录里）
